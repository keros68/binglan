过程发现并修复的三个缺陷：把手在 Dock 展开期间被隐藏导致指针悬空（改为展开期间把手作为行端保持可见）；拖动处理器原先挂在内容 Border 上，鼠标捕获后事件只到达 Window 层级，指针移出窗口后拖动无法结束并悬挂（处理器移至 Window 层级，另加捕获失败守卫）；展开位置的点击失效（见下）。

### 展开位置点击失效（2026-10-09 补充）

用户实测发现悬停展开后点击应用图标无反应。根因：任务栏等其它 AppBar 的位置变更（`ABN_POSCHANGED`，自动隐藏任务栏滑入滑出时频繁发生）会直接触发 Dock 控制器 `Position()`，把展开中的 Dock 拽回条带位——窗口实际位置与应用记录的展开矩形从此失步，点击落在旧矩形上自然无效。修复：展开矩形注册为控制器内部的"浮动位置覆盖"（`SetFloatingOverride`），所有重定位路径（AppBar 通知、显示器/DPI 变化、Explorer 重启、应用内容变化）统一经过它，单一事实源；同时对相同矩形早退，消除悬停期间每 150ms 的无谓移动。修复后连续三次完整的"最大化→悬停展开→真实点击图标→启动应用"自动化验证全部成功（此前同流程约五成失败），应用图标点击恢复。

## 已知限制

- 从文件对话框固定 `C:\Windows\System32\notepad.exe` 这类启动存根时，运行中的应用商店版本不会与固定项合并；在 Dock 中右键运行中的应用选择“固定到 Dock”可正确记录应用 ID。
- AppBar 全屏通知只覆盖置顶窗口且不区分显示器，因此 Dock 每 500 ms（智能隐藏时 150 ms）检查所在显示器上的前台窗口；前台为全屏时智能隐藏的检查也降到 500 ms。
- 保留底部空间失败时，Dock 提示一次并暂时按智能隐藏显示，下次应用设置或 Explorer 重启时重试。
- Dock 窗口不获取焦点，图标不能用 Tab 键选中；键盘用户可继续使用开始菜单、Alt+Tab 和任务栏快捷键。
- Dock 与原生任务栏自动隐藏同时开启时，屏幕底边中间会同时唤出两者。
- 未覆盖：多显示器、显示器插拔、100%/150% 与混合缩放、虚拟桌面、以管理员身份运行的窗口、高对比度下的 Dock 实机外观。

## 悬停放大透明预留高度与跨进程点击穿透验证（2026-11-22）

### 命中隔离设计（不依赖 `HTTRANSPARENT` 跨进程穿透）

- Win32 中 `WM_NCHITTEST` 返回 `HTTRANSPARENT` 仅向同线程窗口透传，无法穿透到其他进程；因此不能让 Dock 或伴生玻璃窗口覆盖预留区。
- **玻璃背景窗口（`DockCompositionBackdrop`）**：`DockGlassSurface` 按 `DockMagnificationRules.ComputeBackdropSurfaceBounds` 将原生毛玻璃窗口的 HWND 边界严格限制在 `DockSurface` 本体范围（例如 150% DPI、48 DIP 图标、1.5 倍放大时，`IceBlueDockWindow` 向上扩展 44 px 透明余量至 134 px，而「冰蓝 Dock 玻璃背景」窗口始终保持 90 px 本体高度，不覆盖上方 44 px 预留区）。
- **Dock 主窗口（`IceBlueDockWindow`）**：非放大态按 `DockMagnificationRules.ComputeHitRegionRect` 通过 `SetWindowRgn` 将窗口命中区域裁剪到 `DockSurface` 本体（排除上方 44 px，最大约 62 DIP 预留区），使 `WindowFromPoint` 与跨进程点击直接命中下方应用；仅在鼠标移入 Dock 开始放大时临时清除区域让图标无裁切放大，鼠标离开且归位动画结束后立即恢复区域裁剪。
- **AppBar 预留条不变**：增加的 44 px（最大约 62 DIP）仅为窗口向上透明预留高度，不改变 AppBar 工作区底边。

### 手工验证步骤与预期结果

1. **前置准备**：在「顶栏与底栏 → 冰蓝 Dock」启用「始终显示，保留底部空间」，打开「尺寸、外观与高级」并开启「悬停放大图标」（测试 1.5 倍与 1.7 倍，图标大小 48 或 64）。
2. **步骤 1（预留区跨进程点击穿透）**：
   - 将一个其他进程的应用窗口（如 Coffee CLI、浏览器或记事本）拖至覆盖 Dock 上方约 50 px 的区域，使其底部按钮、状态栏或标题栏按钮落在 Dock 玻璃上沿上方约 10–40 px 的透明预留带内，先点一下桌面或其他窗口令该应用失焦。
   - **预期结果**：在鼠标未悬停于 Dock 本体时，直接点击该应用落在预留带内的区域，应用立刻获得前台并正常响应点击；用 `WindowFromPoint` 探测该坐标，返回的是下方应用窗口，而非「冰蓝 Dock」或「冰蓝 Dock 玻璃背景」。
3. **步骤 2（放大展开与离开恢复穿透）**：
   - 将鼠标移入 Dock 图标使图标向上放大进入预留区，确认放大图标完整无裁切且可正常点击；随后将鼠标移出 Dock，等待归位动画完成（约 150 ms）。
   - **预期结果**：再次点击步骤 1 中预留带内的下方应用窗口，仍立刻获得前台并响应点击，不再被 Dock 拦截。
4. **步骤 3（AppBar 预留条厚度一致）**：
   - 对比关闭与开启「悬停放大图标」（1.2 / 1.5 / 1.7 倍）时最大化窗口底边位置及 `GetMonitorInfo` 工作区底边。
   - **预期结果**：开关放大前后工作区底边像素值完全一致（例如 2560×1600 @ 150% DPI 下均为 1468 px），增加的 44 px 仅为向上透明预留高度而非 AppBar 厚度。
5. **步骤 4（自动缩小、智能隐藏与多屏）**：固定足够多应用触发自动缩小与横向滚动，以及切到智能隐藏、多显示器环境，确认悬停放大不裁切图标、不压盖真全屏或最大化应用，鼠标离开后立即停表。

2026-11-27 使用 Windows 11 Build 26300 的隔离预览验证 3840×2160 @ 175% 与 2560×1600 @ 150%。两屏同时启用时，32 DIP 与 40 DIP 顶栏的原生窗口高度分别为 56 px 与 60 px。副屏左侧 Dock 的右缘与副屏预留工作区左缘相接。关闭副屏两栏后，副屏的顶部与左侧预留释放，主屏两栏继续显示，副屏恢复的便签仍在。恢复跟随后可将全局 Dock 固定到副屏，主屏仍显示跟随主屏的顶栏。真实拔插、主屏角色互换、旋转和 Explorer 重建另需实机覆盖。

## 副屏任务栏让位恢复

Windows 11 Build 26300，主屏 3840×2160 @ 175%，副屏 2560×1600 @ 150%。直接调用 Release 构建中的任务栏查询和重叠判断，两块屏幕分别匹配各自的 Explorer 任务栏。以旧布局矩形模拟缓存时仍读取当前窗口矩形，另一块屏幕的任务栏不会阻止 Dock 恢复。验证过程仅读取任务栏窗口。

交互验收时，在副屏开启原生任务栏自动隐藏并将 Dock 放在同一边。唤出托盘面板后移开鼠标，检查 Dock 在原生任务栏移出其区域后恢复，快速重开托盘时继续让位。主屏和 Explorer 重启后的副屏应具有相同行为。需要录屏确认滑动过程和交叠帧。

## 顶栏拖动避让、Dock 后台最大化与快速设置

待交互验收。在 Windows 11 单屏及双屏混合缩放下各检查一次，记录 Windows Build、显示器分辨率与缩放比例。

- 顶部信息条设为全透明和智能隐藏。最大化浏览器后按住左键沿顶边拖标签页，确认顶栏不弹出。松手停留约 350 毫秒后可正常唤出。切到 F11 全屏后，顶边不唤出顶栏。
- 选择冰蓝混合方案，在保留空间模式下开启两项最大化隐藏设置，将一个窗口最大化并切到同屏普通窗口，确认 Dock 保持收起且能从把手临时唤出。还原、关闭或最小化最后一个最大化窗口后，Dock 恢复预留。只在另一屏最大化窗口时，本屏保持原状态。
- 在「冰蓝 Dock → 尺寸与高级」开启快速设置按钮，分别在原生任务栏常驻和自动隐藏时点击。确认由 Windows 打开面板，音量、网络和蓝牙可按本机配置使用。关闭面板后 Dock 恢复正常显示规则。切换 Dock 停靠边、重启 Explorer 和关闭按钮后复查入口及布局。
