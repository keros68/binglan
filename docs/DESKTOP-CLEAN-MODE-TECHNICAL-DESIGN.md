# 清爽桌面技术设计与恢复协议

> 状态：已接入正式应用（默认关闭）
>
> 日期：2026-08-04 设计；2026-09-28 接入
> 对应产品需求：`FILE-11`、`FILE-12`

## 1. 结论先行

“清爽桌面”采用 Windows 文档化的 Shell COM 接口控制桌面视图的 `FWF_NOICONS` 位，不移动文件、不改注册表、不结束 Explorer、不发送未文档化消息，也不注入 DLL。

2026-08-04 的只读真机验证已证明：应用可以定位活动桌面视图并读取图标可见状态。2026-08-07 的写入验证进一步发现，当前 Windows 11 build 26200 在只报告 `FVO_VISTALAYOUT` 时可以直接按掩码写入 `FWF_NOICONS`，而显式申请 `FVO_CUSTOMPOSITION` 会返回 `E_NOTIMPL`。因此正式实现先保存恢复检查点，再只按 `FWF_NOICONS` 掩码写入；直接写入失败时回滚并提示“不支持”，不申请 `FVO_CUSTOMPOSITION`，检查点也只记录图标位。

真机还确认：隐藏后 Explorer 会把状态同步到 `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced\HideIcons`，所以隐藏状态会跨 Explorer 重启和重新登录保留。恢复检查点因此是唯一的原状态记录，Explorer 重启后也不需要重新应用。

## 2. 用户可见契约

开启“清爽桌面”后：

- Windows 原生桌面图标暂时隐藏，冰蓝整理盒继续显示桌面入口；
- 桌面文件和文件夹仍在原路径，可从 Explorer 和整理盒正常打开；
- 此电脑、回收站、下载和桌面目录入口必须在隐藏前可用；
- “恢复原桌面”、关闭模式和正常退出恢复开启前的图标状态；
- 不支持或验证失败时保持原生桌面可见，并解释未开启原因；
- 不要求管理员权限，不重启 Explorer，不修改图标坐标。

“移除入口”仍然只删除冰蓝映射，不删除或移动文件。

## 3. 崩溃恢复语义

同一进程在正常退出或可捕获异常时可以立即恢复。进程被强制结束、系统断电或运行时 `FailFast` 时，任何 `finally` 都不保证执行；在“不新增独立常驻守护进程”的架构边界下，无法承诺这种情况下瞬时恢复。

MVP 对“异常恢复”的可验证定义为：

1. 改变 Shell 前先原子保存恢复检查点；
2. 下次启动在创建普通窗口前优先执行恢复；
3. 恢复成功后才清除检查点；
4. 卸载入口调用同一恢复命令；
5. 检查点损坏或 Shell 不可用时不猜测、不反复写入，保持 Windows 当前状态并给出恢复入口。

若产品要求“进程被强杀后也立即恢复”，就需要独立监护机制，会突破单一应用宿主边界，应作为新的架构决策，而不是隐藏在本功能实现中。

## 4. 模块边界

正式接入时保持两层：

- `BingLan.Core`：检查点模型、状态机、迁移、逐位恢复规则和可脱离 Windows 的测试；
- `BingLan.App`：Shell COM 绑定、Explorer 生命周期观察、原子文件保存以及应用启动/退出接线。

不建立通用 Shell 插件框架。桌面可见性适配器只服务“读取快照、隐藏、恢复”三个当前调用。

## 5. 最小持久化模型

恢复检查点与普通主题分离，属于本机运行状态，不允许导出：

```text
desktop-icons-recovery.json
SchemaVersion = 1
Phase = Prepared | Applied | Restoring
OriginalIconsHidden
CreatedAtUtc
```

只保存本功能拥有的图标位，不保存并回写整组 Shell 标志，避免覆盖用户或 Windows 在会话中修改的其他选项。用户意图（是否开启）作为 `CleanDesktopEnabled` 保存在 Schema v16 的个人状态中，不进入主题包。

## 6. 状态转换

### 6.1 开启

1. 在第一个分组盒中补齐此电脑、回收站、下载和桌面目录入口（已存在的不重复添加；没有分组盒时新建一个）；任一入口无法添加时不隐藏图标，并说明缺少哪个入口。
2. 获取新的活动桌面视图并读取图标位；图标已处于隐藏状态时拒绝开启并提示先在桌面右键菜单“查看”中显示图标——没有本次隐藏的记录，关闭时将无法恢复，不能把无记录的隐藏报告为开启成功。
3. 以临时文件替换方式写入 `Prepared` 检查点，落盘成功前不修改 Shell。
4. 仅以 `FWF_NOICONS` 为掩码设置隐藏，并重新读取验证。
5. 验证通过后原子更新检查点为 `Applied`，再保存开关并更新界面。
6. 写入或验证失败时按检查点恢复原图标位并提示原因；恢复也失败时保留检查点，下次启动再恢复。

### 6.2 关闭或退出

1. 将检查点更新为 `Restoring`。
2. 重新获取当前桌面视图，不复用之前的 COM 对象。
3. 仅恢复原始 `FWF_NOICONS` 位并验证。
4. 验证成功后删除检查点。关闭模式同时保存开关为关闭；正常退出保留开关，下次启动重新应用。

恢复幂等：没有检查点时不做任何写入，重复执行与执行一次结果相同。检查点无法解析、缺少任一字段或版本更新时，改名为 `.invalid` 保留，不猜测原状态、不写 Shell。启动时恢复失败则本次不自动开启清爽桌面、开关置为关闭，并用托盘通知提示用户从桌面右键菜单重新显示图标。`.invalid` 文件同时作为“原状态未知”的标记跨重启保留：存在时不自动开启；图标仍隐藏时手动开启会被拒绝并提示先显示图标，避免把未知状态记成原状态；看到图标可见（开启时或用户接管时）后删除该标记。检查点只在文件确实不存在时视为无需恢复，其他读取错误都按恢复失败处理。

显式关闭不受这条幂等规则约束：开关开着说明隐藏状态由本功能持有，检查点缺失、损坏或恢复失败而图标仍隐藏时，直接把图标位恢复为显示并如实提示，不再把“无记录可恢复”报告为成功（2026-10-21 修复：此前该情形被虚报为“已恢复”，图标会永久卡在隐藏）。启动、退出和 `--restore-taskbar` 的自动恢复仍保持“无检查点即无事可做”，避免覆盖用户自行隐藏的桌面。

### 6.3 Explorer 重启和外部修改

- 每次操作都重新获取桌面视图，Explorer 重启后不会使用失效的 COM 引用；
- 隐藏状态由 Windows 跨 Explorer 重启保留，因此不需要重新应用；
- 开启期间每 5 秒只读检查一次图标位；发现图标重新显示（桌面右键菜单或其他工具），视为用户接管：删除检查点、关闭开关，不再写入；
- 获取失败时本轮跳过，不阻塞 UI，保留检查点供稍后或下次启动处理。

## 7. 并发和失败边界

- 应用内所有 Shell 调用经单通道串行执行，并在后台线程运行；开启/关闭请求按顺序处理，后到的关闭不会被先到的开启覆盖。`--restore-taskbar` 是独立进程，与运行中的应用通过同一个跨进程互斥锁串行读写检查点和桌面视图；
- 写入后重新读取验证，不基于缓存推断成功；
- 设置开关在操作期间禁用，完成后按实际状态刷新并显示结果或失败原因；
- 网络、桌面扫描和图标提取不参与恢复事务；
- 退出时恢复最多等待 5 秒，超时不阻止退出，检查点保留到下次启动；
- 进程被强制结束时无法即时恢复：图标保持隐藏，直到下次启动冰蓝桌面或卸载时运行 `--restore-taskbar`。

## 10. 正式接入真机结果（2026-09-28）

环境：Windows 11 家庭中文版 build 26200，单屏 2560 × 1440，125% 缩放。测试使用 `--interactive-qa` 隔离数据目录，读取工具复用正式 `DesktopShellView`。原始文件夹标志 `0x40200224`，图标可见，`HideIcons = 0`。

| 场景 | 结果 |
| --- | --- |
| 只读查询 | 标志 `0x40200224`，与阶段 0 实验一致，无变化 |
| 启动时开关为开启 | 隐藏图标（`0x40201224`，`HideIcons = 1`），检查点 `Applied`；分组盒补入此电脑、回收站、桌面，已有的下载入口未重复 |
| 强制结束进程 | 图标保持隐藏，检查点保留 |
| `--restore-taskbar`（卸载同一命令） | 退出码 0，图标恢复，检查点删除；再次执行仍为 0 且无变化 |
| 强制结束后重新启动 | 启动前先恢复，再按开关重新隐藏，检查点 `Applied` |
| 外部把图标改为可见 | 5 秒内识别为用户接管，检查点删除，开关保存为关闭，之后不再写入 |
| 托盘“退出” | 图标恢复、检查点删除，开关保持开启 |
| 检查点内容为 `{}` 时运行 `--restore-taskbar` | 退出码 1，检查点改名为 `.invalid`，桌面标志未被写入 |
| 应用运行中执行 `--restore-taskbar` | 退出码 0，图标恢复；运行中的应用随后识别为接管并关闭开关 |
| 图标已隐藏且检查点无效时启动 | 不自动开启，开关置为关闭，图标保持现状并给出托盘提示 |

未覆盖：Explorer 重启中途开启/关闭、多显示器与 100%/150% 缩放、注销或关机时的退出恢复。自动测试覆盖规则、检查点和设置开关（核心烟雾测试 5 项、WPF 烟雾测试 1 项），不替代以上真机场景。

## 11. 无记录关闭兜底真机结果（2026-10-21）

正式使用中暴露出一个缺陷：检查点丢失后关闭清爽桌面被报告为“桌面图标已恢复”，图标实际保持隐藏（`HideIcons = 1`、无检查点文件、开关显示关闭）。根因是两个洞叠加：图标已隐藏时开启会静默成功且不留检查点（缺陷 1），检查点缺失时关闭被报告为成功且不写 Shell（缺陷 2），记录一旦丢失即永久卡死。修复为“图标已隐藏时拒绝开启、显式关闭兜底恢复显示”，并补齐开启/关闭/接管/恢复日志。

环境同第 10 节（Windows 11 build 26200，单屏 125%）。验证用链接正式源码的临时 harness 驱动真实 Shell，起始状态即缺陷形态（图标隐藏、无检查点）：

| 场景 | 结果 |
| --- | --- |
| 图标已隐藏且无检查点时开启 | 被拒绝并提示先显示图标，未写 Shell，未产生检查点 |
| 开启后删除检查点再关闭 | 图标直接恢复显示，日志记录“检查点缺失……已直接恢复显示” |
| 正常开启/关闭往返 | 隐藏、按检查点恢复、检查点删除均正常 |
| 验证收尾 | 图标恢复可见，`HideIcons` 同步回 0 |

未覆盖：Explorer 重启中途关闭、多显示器。自动测试新增“清爽桌面无记录时关闭仍恢复显示”规则回归项；全量核心烟雾测试通过，UI 烟雾测试中顶栏搜索物理输入类用例在本机存在与本改动无关的既有抖动。
